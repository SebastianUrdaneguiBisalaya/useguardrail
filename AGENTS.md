# AGENTS.md

Standards and best practices for building, maintaining, and publishing a Node.js library written in TypeScript, bundled with `tsup`, and distributed on npm.

**This is a template repository.** Sections 1-10 below are generic and apply to any Node.js + TypeScript + tsup library. The final section, "Project context template: SDK for a third-party API," is a fill-in-the-blanks checklist for the specific case this template is meant for — wrapping a third-party HTTP API as an SDK — and should be adapted (or removed) once the template is instantiated for a real project.

## 1. Project structure

```
src/
  index.ts        # single public entry point (barrel file)
  ...             # internal modules, not exported directly
tests/
  ...             # vitest tests, mirroring the structure of src/
dist/             # generated by tsup, never versioned
```

- `src/index.ts` is the **only** file that decides the library's public surface. Anything meant to be consumable from outside must be explicitly re-exported there (`export { Foo } from "./foo"`, `export type { FooOptions } from "./foo"`).
- Anything inside `src/` that doesn't pass through `index.ts` is not public API: it can be freely refactored without being a breaking change.
- Don't use `export *` on large internal modules: prefer explicit named exports to control exactly what gets frozen as the public contract.

## 2. TypeScript

- `strict: true` always. Don't relax type-checking rules just to "make it compile".
- Every public type, interface, or function must be exported from `src/index.ts` with `export type` / `export` as appropriate (`verbatimModuleSyntax` in this project enforces this explicit distinction).
- Exported types should be documented with TSDoc (`/** ... */`) when the name isn't self-explanatory, especially for configuration options and public function parameters — these comments become the autocomplete/hover text SDK consumers will see.
- Don't use `any` on the public surface. If an external type is unknown, use `unknown` and force explicit narrowing.
- Prefer `type` over `interface` unless declaration merging or extended inheritance is needed; be consistent across the repo.
- **No object-oriented `class` usage anywhere in `src/`.** Model the domain with `type`/`interface` and implement behavior with arrow functions or classic (`function`) declarations. State that would otherwise live on a class instance lives instead in a closure returned by a factory function (`createFoo(config): Foo`) or in a plain object. No inheritance, no `this`-based method binding, no abstract classes/decorators for internal logic.
- **Consequence for consumer-facing instantiation (`new MySdk()`):** in JavaScript/TypeScript, `new` only works on something that acts as a constructor — a `class`, or a classic (non-arrow) function used as one. An arrow-function factory can never be called with `new`. Since this project bans classes, don't try to fake constructor semantics with a classic function just to unlock `new` — that reintroduces the same problem (a hidden constructor) under a different name. Instead:
  - Expose a single factory as the only way to get an instance: `export function createClient(config: ClientConfig): Client { ... }`, returning a plain object (or closure) that satisfies the `Client` type.
  - For consumers on frameworks that conventionally instantiate dependencies with `new` (e.g. NestJS), document the idiomatic adaptation instead of chasing `new` support — a NestJS custom provider:
    ```ts
    {
      provide: MY_SDK_CLIENT,
      useFactory: () => createClient({ secretKey: process.env.SECRET_KEY! }),
    }
    ```
  - `new MySdk()` syntax is only achievable if the whole client is implemented as an actual constructor (`class` or classic function) — which this project's style rule rules out by design. Treat "factory function + framework-native DI adapter documented in the README" as the supported pattern, not a workaround.

## 3. Bundling with tsup (ESM + CJS + types)

The package must be consumable both with `import` and with `require`:

```ts
import { Client } from "your-package-name";
```
```js
const { Client } = require("your-package-name");
```

This is achieved by:

- `tsup.config.ts` compiling to `format: ["esm", "cjs"]`, with `dts: true` (or `{ resolve: true }`) to generate the `.d.ts` files for each format.
- `package.json` with an explicit `exports` field per subpath, specifying `types`, `import`, and `require` — Node.js and modern bundlers resolve via `exports`, not `main`/`module` (those fields are kept only as fallback for older tooling).
- Key order inside each `exports` condition matters: `types` always first, then `import`/`require`.
- Never commit `dist/`. It's generated during CI/build and published via `files` in `package.json`.

### Checklist before publishing

1. `pnpm run build` generates `dist/index.mjs`, `dist/index.cjs`, `dist/index.d.mts`/`dist/index.d.cts` (or a shared `.d.ts`) with no errors.
2. `pnpm run typecheck` (`tsc --noEmit`) passes clean.
3. `pnpm run lint` (biome) passes clean.
4. `pnpm run test` passes.
5. Test the packed package locally before the first real publish:
   ```bash
   pnpm pack
   # in another test project:
   npm install /path/to/your-package-name-x.y.z.tgz
   ```
   Verify that both `import` (ESM) and `require` (CJS) work, and that types resolve correctly in the editor.
6. **Publishing to npm must never be run manually or by an AI agent.** This project publishes exclusively through the GitHub Actions workflow at `.github/workflows/publish.yml`, which runs automatically on every push to `main`. Never run `npm publish` / `pnpm publish` from a local machine or from an agent session — it's a public, irreversible action (a version can't be "unpublished" without restrictions), and doing it outside CI skips the required typecheck/lint/test/build gate.

### CI publish flow (`.github/workflows/publish.yml`)

- **Trigger**: a GitHub Release being published (`release: types: [published]`). Merging to `main` does **not** publish anything by itself — publishing is a separate, deliberate step: bump `version` in `package.json` (following semver, see section 4), merge that to `main`, then create a GitHub Release (tag matching the new version is recommended, e.g. `v1.2.0`) to trigger the actual npm publish.
- **Gate**: `typecheck` → `lint` → `test` → `build` must all pass before publishing is attempted.
- **Version guard**: before publishing, the workflow checks `npm view <name>@<version>` against the current `package.json` version and skips the publish step if that version is already on the registry — a safety net in case a release is edited/republished without a version bump.
- **Required GitHub secret**: `NPM_TOKEN`.
  - Generate it on [npmjs.com](https://www.npmjs.com) → avatar → *Access Tokens* → *Generate New Token* → **Automation** type (this type is meant for CI and bypasses the 2FA-for-publish prompt; it must have publish permission on this package/scope).
  - Configure it in GitHub at: repository → **Settings** → **Secrets and variables** → **Actions** → **New repository secret** → name it exactly `NPM_TOKEN`, paste the token value.
  - Never commit this token to the repo or print it in workflow logs.
- The workflow publishes with `--provenance`, which requires `permissions: id-token: write` (already set in the workflow) and works for public packages published from a public GitHub repo — this gives consumers a verifiable link between the published package and this repo's build.
- The `if: ${{ !github.event.repository.fork }}` guard prevents the workflow from publishing from a fork.

## 4. Versioning and changes

- Follow [Semantic Versioning](https://semver.org/): `MAJOR.MINOR.PATCH`.
  - `MAJOR`: breaks the public API (changes an exported signature, removes an export, changes documented behavior).
  - `MINOR`: new backwards-compatible functionality.
  - `PATCH`: backwards-compatible fixes.
- Any change to `src/index.ts` (adding/removing/changing an export) is, by definition, a change to the public surface: treat it with the same care as an API change, not as an internal detail.
- Keep a `CHANGELOG.md` (or use `changesets`/`release-please` as the project grows) so whoever updates the dependency knows what changed.

## 5. Quality and CI

- Lint and format with `biome` (already configured in `biome.json`).
- `.editorconfig` sets the baseline (indentation, charset, line endings, final newline) for files Biome doesn't format — Markdown, YAML/workflow files, etc. — and applies at the editor level even before a formatter runs.
- Tests with `vitest`, mirroring the structure of `src/` inside `tests/`.
- Don't merge to `main` with `typecheck`, `lint`, or `test` failing.
- The `prepublishOnly` script must run `build` (and optionally `test`) to avoid publishing an outdated or broken package.
- **Git hooks via [husky](https://typicode.github.io/husky/)** enforce the checks above locally, before code even reaches CI:
  - `prepare: "husky"` in `package.json` installs the hooks automatically on `pnpm install` (for every contributor, not just whoever set it up).
  - `.husky/pre-commit` runs `lint` + `typecheck` — fast checks, on every commit.
  - `.husky/commit-msg` rejects commit messages that don't follow [Conventional Commits](https://www.conventionalcommits.org/) (see `CONTRIBUTING.md`).
  - `.husky/pre-push` runs `test` + `build` — slower checks, before code leaves the machine.
  - Hooks are a local safety net, not a substitute for CI: CI must run the same checks independently, since hooks can be skipped locally (`--no-verify`).

## 6. General library best practices

- **Zero runtime dependencies whenever possible.** Every dependency added to `dependencies` is inherited by every consumer of the SDK. Prefer Node's standard library/native fetch before adding an external dependency.
- **Pin every dependency to an exact version.** Always install with `pnpm add -E <package>` (`-D -E` for dev dependencies) — never accept the default caret (`^`) range — so this project's own install and every consumer's install resolve to the exact version that was tested. Set `save-exact=true` in `.npmrc` as a backstop so a plain `pnpm add` can't silently reintroduce a range.
- **`sideEffects: false`** in `package.json` if the package has no module-level side effects (global polyfills, etc.), to allow tree-shaking on the consumer's side.
- Don't use runtime-specific code (browser-only or Node-only APIs) in the main entrypoint unless the SDK is explicitly meant for a single environment (see the project context section below: this SDK is Node-only).
- Never log to `console` inside the library except behind an explicit debug flag controlled by the consumer.
- Don't throw generic exceptions (`throw new Error("something failed")`): define and export your own error classes so the consumer can do `instanceof` and handle specific cases.
- **If the SDK handles credentials or secrets (API/secret keys, private tokens), it must be server-side only, and this must be enforced, not just documented.** It uses a *secret key*, which must never reach a browser, a mobile client, or any bundle shipped to an end user — anyone who obtains it can act on the account it authenticates.
  - The client (e.g. `Client`) must be constructed and used only from server-side code (a Node.js backend, an API route, a serverless function) — never imported into client-side/browser bundles.
  - Add a runtime guard in the entrypoint/client constructor that detects a browser-like environment (e.g. `typeof window !== "undefined"`) and immediately throws a descriptive error (e.g. `EnvironmentError: Client must only be used server-side. Never expose your secret key to the client.`) instead of silently continuing. Fail loudly and immediately — don't let a misconfigured bundler ship a broken/insecure client.
  - `package.json` must not declare a `browser` field, and the package should not advertise browser compatibility anywhere (README, `keywords`, `engines`) — this discourages bundlers from trying to include it in a client bundle in the first place.
  - Document prominently in the README (top of the file, not buried) that this SDK must run only on a trusted server, and that any client-side flow (e.g. tokenizing sensitive data) must instead use the third-party provider's own client-side/JS SDK with a public/non-privileged key, sending only the resulting non-sensitive token to the backend where this SDK runs.

## 7. Local development workflow

The exact sequence of commands — for a human contributor or an AI agent — to run after making a source change, how to try the built package locally, and what to run before opening a pull request now lives in the **"Development"** section of [README.md](./README.md). Follow that instead of duplicating it here; update it there if the workflow changes.

## 8. Target environment: server, client, or both

Before writing SDK code for a specific project (not while working on the generic template), check whether the project context states if the SDK is meant to run server-only, client-only, or both, and apply the corresponding rules:

- **server-only** (a Node.js backend, API route, serverless function) — the default assumption in this template: apply the secret-key handling in section 6 as written.
- **client-only** (browser/mobile) — none of section 6's secret-key/server-side-only rules apply the same way, since there's no server-side code to guard; use a public/non-privileged key model instead.
- **both** — the codebase needs a clear boundary (e.g. separate entry points/exports) between the server-side client that holds secrets and any client-side helper that doesn't.

This choice determines which practices from section 6 and from the "Client design"/"Security" parts of the project-context section actually apply, so don't guess it from the API's shape.

## 9. Provider plugins (optional monorepo layout)

**This template already ships with this layout applied** (`packages/core`, wired up via `pnpm-workspace.yaml`), even before any provider package exists — treat it as the baseline going forward, not something to opt into later. Everything below explains why it's shaped this way and how to add a provider package to it.

If the SDK supports pluggable external providers (e.g. storage backends: S3, Cloudflare R2, GCS) and consumers should only install the dependencies a given provider actually needs, split the SDK into a `pnpm` workspace instead of a single package:

```
packages/
  core/                    # @mypackage/core — Client, http, errors, environment guard
  s3/                      # @mypackage/s3 — S3 provider, peer-depends on core
  cloudflare-r2/           # @mypackage/cloudflare-r2 — same pattern
pnpm-workspace.yaml
```

- Each provider is its own npm package (`@mypackage/s3`, `@mypackage/cloudflare-r2`), published independently, so a consumer runs `pnpm add -E @mypackage/s3` and only pulls in that provider's own dependencies (e.g. `@aws-sdk/client-s3`) — someone who only needs Cloudflare R2 never installs the AWS SDK.
- Every provider package declares `@mypackage/core` as a `peerDependency`, not a regular `dependency`, so a single core version is shared instead of duplicated across `node_modules`.
- `packages/core` is the only package allowed to define the shared `Client` factory, error classes, and the environment guard from section 6. Providers implement a narrow adapter type exported from core (e.g. `type StorageProvider`) and get registered into the client the consumer already created — consistent with the no-classes rule in section 2 (an adapter is a plain object/factory, not a subclass).
- Version each package independently with [`changesets`](https://github.com/changesets/changesets) rather than manually bumping every `package.json` in lockstep — it tracks which packages actually changed and avoids publishing a provider whose only change was an unrelated core bump.
- The publish gate from section 3 (`typecheck` → `lint` → `test` → `build`) still applies, run across the whole workspace (`pnpm -r run typecheck`, etc.) before any package is published.
- If the SDK has no pluggable providers, skip this section entirely and keep the single-package layout from section 0/1.

## 10. Documentation website

- This template does not ship a documentation website by default. If one is added later (Docusaurus, Nextra, VitePress, etc.), give it its own top-level directory — `apps/website/` if the repo already has the `apps/*` + `packages/*` split (add `apps/*` back to `pnpm-workspace.yaml`), or a plain `website/` at the repo root (sibling to `packages/`) otherwise.
- The website must never be published to npm: keep it out of every package's `files` field / add it to `.npmignore` so it can't leak into a published tarball.
- Deploy the website independently of the SDK's npm release (its own CI job/workflow) — docs can and should ship more often than the package itself (e.g. after a README/example fix that doesn't warrant a version bump).

# Project context template: SDK for a third-party API

This section is a checklist to fill in (and rename) once this template is used to build an SDK for a specific third-party HTTP API — e.g. "Project context: Node.js SDK for `<Provider>`". Replace `<Provider>` and `Client` below with the actual API/service and the client class name you choose. If the resulting SDK isn't payments-related, adjust "Security" to match the actual sensitivity of the credentials/data involved — the server-side-only enforcement in section 6 still applies to any secret key, not just payment ones.

## 0. Concrete file structure

The generic layout in section 1 above (top of this file) says "one file per internal module" in the abstract. For an SDK wrapping a third-party API with multiple resources, that concretely looks like this — nested under `packages/core/` per the monorepo layout in section 9:

```
packages/core/
  src/
    index.ts              # barrel file — re-exports only the public surface
    client.ts             # createClient() factory: config, shared request logic, type Client
    http.ts                # low-level fetch wrapper: base URL, headers, timeouts, retries
    errors.ts             # ApiError, AuthenticationError, ValidationError, etc.
    environment.ts         # the server-side-only runtime guard (section 6)
    <resource>/            # one directory per API resource (e.g. users/, orders/, webhooks/)
      index.ts             # the resource's methods (create/get/list/update/delete), as factory functions
      types.ts             # request/response types for this resource only
  tests/
    client.test.ts
    <resource>/
      index.test.ts        # mirrors src/<resource>/index.ts
```

- Each resource directory is self-contained: its own types file, its own methods file, its own tests. A change to how `<Provider>` shapes one resource's response never touches another resource's files.
- `client.ts` composes the resources (e.g. `users: createUsersResource(deps)` inside the object `createClient` returns), it doesn't implement resource-specific logic itself. No classes — see section 2's no-OOP rule, which applies here too.
- `errors.ts` and `environment.ts` are two of the few internal files re-exported in full from `index.ts` (the error classes and, if needed, the guard's error type) — everything else in `src/` stays internal unless explicitly re-exported (see section 1 at the top of this file).

## 1. Client design

- Expose a main client created with the consumer's credentials, instead of loose functions that repeat the API key as a parameter on every call. Per section 2, this is a factory function, not a class instantiated with `new`:
  ```ts
  const client = createClient({ secretKey: "sk_..." });
  await client.resource.create({ ... });
  ```
- Organize `<Provider>` API resources (e.g. users, orders, webhooks) as separate modules/namespaces within the client, each in its own file inside `src/`, re-exporting from `index.ts` only what should be public (request/response types, the client, error classes).
- The client **must not** depend directly on environment variables (`process.env.PROVIDER_API_KEY`) inside the SDK: credentials are always explicitly injected by the consumer when constructing the client. Reading `process.env` is the responsibility of the app using the SDK, not the SDK itself.

## 2. API error handling

- Never let a raw HTTP error (a rejected `fetch`, a 4xx/5xx status) propagate as-is to the consumer. Map `<Provider>`'s error responses to your own typed error classes, exported from `index.ts` (e.g. `ApiError`, `AuthenticationError`, `ValidationError`), including the code and message returned by the API for debugging.
- Validate input types at compile time (TypeScript) and, when the cost of a runtime error is high (money, PII, destructive operations), consider runtime validation too, since the consumer may be in plain JS without type checking.

## 3. Security

- If this SDK uses a secret/API key, it's server-side only — see the general server-side-only rule in section 6. Concretely: never import `Client` in a browser bundle, and for any client-side flow use `<Provider>`'s own client-side/JS SDK with a public/non-privileged key, sending only the resulting non-sensitive token to the backend where this SDK runs.
- Never log (`console.log`, `console.error`, telemetry) the full body of a request/response that may contain sensitive data or secrets. If debug logging is added, explicitly redact those fields.
- Don't include secrets in error messages or in serializable objects the consumer might accidentally log.
- All communication with `<Provider>`'s API must go over HTTPS; don't expose options that allow downgrading to HTTP.
- Don't cache or persist sensitive data to disk or shared memory beyond the lifecycle of the request that uses it.

## 4. External API compatibility and stability

- Internally version against a known version of `<Provider>`'s API. If `<Provider>` introduces breaking changes to its API, the SDK should document which API version it was tested/is supported against.
- Request/response types for each `<Provider>` resource should live in one file per resource (e.g. `src/<resource>/types.ts`) so a change in the shape of an endpoint is easy to locate and update.
- Cover with tests (mocking the HTTP layer, never hitting the real `<Provider>` API in unit tests) at least the happy path and error mapping for each supported resource.

## 5. Documentation for consumers

- `README.md` must include, at minimum: installation, client initialization, one example per main resource, and how to handle the typed errors the SDK exposes.
- Every public exported function/method must have TSDoc with at least a one-line description and, when applicable, a usage example — this is what the consumer sees on hover in their editor, not just the README.

This section is a template to be specialized per project. Sections 1-10 above are the reusable, generic part of this template for any Node.js + TypeScript + tsup library.
